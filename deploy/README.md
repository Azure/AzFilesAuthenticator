# Deploy / E2E Test Helpers

This directory contains scripts for provisioning real Azure infrastructure and
running end-to-end (E2E) tests that actually mount an Azure Files SMB share
via managed identity — as opposed to the mocked unit tests in `test/`.

- **`test-vms.sh`** — one-shot: builds packages, provisions a resource group
  (storage account + share + VNet + VMs), installs the package directly on
  each VM's host OS, and runs `test/run_e2e_tests.sh` there.
- **`run_e2e_in_container.sh`** — runs `test/run_e2e_tests.sh` for one distro
  inside a Docker container on an *existing* VM, reusing that VM's network
  path to Azure IMDS and the storage account. Use this to validate additional
  distros beyond the ones `test-vms.sh` provisions VMs for, without spinning
  up a VM per distro.

Both require real Azure credentials (`az login`) and cost real money while
resources are running — remember to tear down the resource group when done.

## Prerequisites

- `az` CLI logged in (`az login`) with access to the target subscription.
- `docker` installed locally (for building packages) and on the target VM
  (for `run_e2e_in_container.sh`).
- `ssh`/`scp`/`rsync` available locally.
- An SSH key pair (auto-generated by `test-vms.sh` at
  `~/.ssh/azfilesauth-test` if one doesn't already exist).

## `test-vms.sh`: full provision + install + test

Builds packages for Ubuntu 24.04, RHEL 9, and SLES 15 SP7, provisions (or
reuses) a resource group with a storage account + SMB share + one VM per
distro (each with a system-assigned managed identity and the
`Storage File Data SMB MI Admin` role on the storage account), installs the
package directly on each VM, and runs `test/run_e2e_tests.sh` there via SSH.

```bash
bash deploy/test-vms.sh                          # build + provision + test all 3 distros
bash deploy/test-vms.sh --skip-build              # reuse already-built PACKAGES/
bash deploy/test-vms.sh --skip-infra              # reuse an existing resource group/VMs
bash deploy/test-vms.sh --distro=ubuntu           # only ubuntu | rhel9 | sles15
```

Useful environment overrides (see the top of the script for the full list):

| Variable | Default | Purpose |
| --- | --- | --- |
| `SUBSCRIPTION_ID` | (hardcoded default) | Target subscription |
| `RESOURCE_GROUP` | `sprasad-azfiles-final-test` | Resource group to create/reuse |
| `LOCATION` | `centralindia` | Azure region |
| `STORAGE_ACCOUNT` | auto-generated | Reuse an existing storage account |
| `USER_MI_CLIENT_ID` | (unset) | Enables user-assigned MI scenarios |
| `RUN_MI_LIFECYCLE_TESTS` | `0` | Set to `1` to run the real mount/refresh scenarios |
| `SSH_PRIVATE_KEY` | `~/.ssh/azfilesauth-test` | SSH key used to reach the VMs |

The VM names it manages are `azfiles-ubuntu24-vm`, `azfiles-rhel9-vm`, and
`azfiles-sles15sp7-vm`. Re-running with `--skip-infra` reuses whichever of
these already exist in `$RESOURCE_GROUP` instead of recreating them.

## `run_e2e_in_container.sh`: test another distro against an existing VM

Once a VM like the ones above exists (e.g. `azfiles-ubuntu24-vm`, created by
`test-vms.sh` or otherwise), you can validate *other* distros — anything with
a `test/distro_run/<distro>.containerfile` — by running them as privileged
Docker containers on that VM. The container reuses the VM's network path, so
managed-identity token requests (IMDS) and the SMB connection (port 445) both
work exactly as they would for a process running directly on the VM.

### 1. Build packages for every distro locally

```bash
./test/test_package_builds.sh                 # all distros
./test/test_package_builds.sh ubuntu22 rhel9  # or just a subset
```

This populates `test/artifacts/<distro>/*.deb|*.rpm`.

### 2. Copy the repo and a built package to the VM

```bash
VM_IP=<vm-public-ip>
SSH_KEY=~/.ssh/azfilesauth-test

# Sync the repo (skip local build output — it's not needed on the VM).
rsync -az --delete -e "ssh -i $SSH_KEY -o IdentitiesOnly=yes -o StrictHostKeyChecking=no" \
  --exclude 'PACKAGES' --exclude 'test/artifacts' --exclude '.git' \
  ./ azureuser@"$VM_IP":~/AzFilesAuthenticator/

# Copy just the one distro's package artifact you want to test.
scp -i "$SSH_KEY" -o IdentitiesOnly=yes -o StrictHostKeyChecking=no -r \
  test/artifacts/ubuntu22 azureuser@"$VM_IP":~/AzFilesAuthenticator/test/artifacts/ubuntu22
```

### 3. Run the e2e test for that distro, on the VM

```bash
ssh -i "$SSH_KEY" -o IdentitiesOnly=yes -o StrictHostKeyChecking=no azureuser@"$VM_IP" \
  "cd ~/AzFilesAuthenticator && sudo STORAGE_ACCOUNT=<storage-account> FILE_SHARE=testshare \
     bash deploy/run_e2e_in_container.sh ubuntu22 test/artifacts/ubuntu22/azfilesauth_*.deb"
```

`run_e2e_in_container.sh <distro> <path-to-package>`:
1. Builds a run image from `test/distro_run/<distro>.containerfile` with the
   package installed (same image used for basic install validation).
2. Runs it with `--rm --privileged`, mounting the VM's `test/` and `src/`
   directories read-only, so it always exercises the exact test/source code
   currently on the VM (not whatever was baked into the package at build
   time).
3. Installs the extra packages that distro needs for a *real* mount (cifs
   mount tools + `klist`), forces a `FILE:`-based krb5 credential cache (see
   below), then runs `test/run_e2e_tests.sh` with `RUN_MI_LIFECYCLE_TESTS=1`.

Required environment variables: `STORAGE_ACCOUNT`. Optional: `FILE_SHARE`
(default `testshare`), `USER_MI_CLIENT_ID` (to also exercise user-assigned MI
scenarios).

### Why `run_e2e_in_container.sh` forces a `FILE:` krb5 cache

A plain `docker run` process has no login session. MIT krb5's default
`KEYRING:`-based credential cache relies on session/keyring semantics that a
login session (PAM) normally sets up, which don't exist in a container. Without
forcing `default_ccache_name = FILE:/tmp/krb5cc_%{uid}` in `/etc/krb5.conf`,
`azfilesauthmanager set` fails with an rcache/replay-detection error that does
**not** occur when run directly on the VM's host OS. `test-vms.sh` already
applies this same override for RHEL/SLES VMs; the container script applies it
unconditionally, for every distro, since none of them have a session either.

### Adding a new distro

Add an entry to the `EXTRA_INSTALL` map in `run_e2e_in_container.sh` with the
package names that distro needs for `mount.cifs` and `klist`, matching an
existing `test/distro_run/<distro>.containerfile`. The package includes its
Python dependencies in `/opt/azfilesauth/venv`.

### Known limitations of the container approach

- **`ubuntu20` (focal)**: ships krb5 1.17, which fails with a replay-detection
  error unrelated to azfilesauth itself; this distro is already deprioritized
  elsewhere in this repo's build/test history.

All `test/distro_run/<distro>.containerfile` images now bake in `cifs-utils`
and `keyutils` directly, so a real SMB mount works out of the box for every
distro they build. For `rhel9`/`rhel10`, this required an extra repo: an
**unregistered** RHEL UBI image only has the free `ubi-9-*-rpms` /
`ubi-10-*-rpms` repos enabled (hosted at the public `cdn-ubi.redhat.com`
mirror, no subscription needed), and `cifs-utils`/`keyutils` simply aren't
published in that curated repo set at all — this is independent of the
"not registered with an entitlement server" warning dnf prints, which is
harmless and doesn't block other packages from installing. Registering with
`subscription-manager` alone wouldn't fix it either, since it wouldn't change
which repos are enabled. The containerfiles instead add the freely-accessible,
ABI-compatible CentOS Stream `BaseOS` mirror (`mirror.stream.centos.org`) just
to pull those two packages, then install the azfilesauth package as before.

## Cleaning up

Both scripts create real, billable Azure resources. When you're done testing:

```bash
az group delete --name <resource-group> --yes --no-wait
```
